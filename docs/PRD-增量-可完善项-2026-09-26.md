## 1. 摘要：最值得做的前 3 项（A1 / B1 / B2 —— 三项**均已交付**，commit 见 §5）

### 🥇 第一优先（**已完成**）：**A1 · JSON 备份恢复（R10.2）** —— 一句话：我们让ta留的备份，现在导不回来

> ✅ **已交付 `9f484a0`**（API `POST /data/restore/preview` → `POST /data/restore` 两段式；前端 `BackupRestoreCard`；core `parseExportPayload` / `summarizeExportPayload`；`/why-numbers` ⑲ —— 见 §5）。
> 下列论证保留为 **2026-09-26 复查当时的原始判断**（其「未实现」结论已随交付失效）——**权威状态见 §5 与代码**。

**（当时的判断）理由不是「少了个功能」，而是「承诺与实现不一致」。**

（当时）产品在多处**反复告诉用户**这个 JSON 可以完整恢复：
`SettingsDataPage` 写着「JSON **可完整恢复**」、`/api/data/export` 的注释写着「完整可恢复备份」、
而 R11.6「留一份备份」按钮下载的**正是这个文件**。但整个代码库里**没有任何一条恢复路径** ——
API 只有 `POST /data/import/weights`（仅体重 CSV），前端只有 CSV 体重导入。

这意味着：上一轮我们刚做的 R11.6（温柔地提醒用户"留一份备份"）在结果上是**空转**的 ——
用户照做了，手里多了一个 JSON，但换设备或误删之后**导不回来**。数据主权的最后一公里没接通。

对单人自用场景，这是最真实的风险：**没有第二个人帮你留底**。
而"数据越久越有价值"正是这个产品沉淀感的来源。

> **回填结论**：上述「最后一公里」已随 `9f484a0` 闭环 —— 恢复前先展示备份内容（各实体条数 + 日期跨度），
> **同日覆盖 / 不同日追加、绝不静默覆盖**，写入单事务（全有或全无）。本项**不再是待办**。

### 🥈 第二优先（**已完成**）：**B1 · 食物搜索的相关性排序 + 加载更多** —— 食物库翻了 4 倍，搜索却没跟着长

> ✅ **已交付 `f6a6e95`**（前端改走相关度优先的 `/foods/search`；见 §5）。下列为交付前判断。

食物库刚从 443 扩到 **1773 条**。但搜索链路有两个没跟上：

1. **完全没有相关性排序** —— `foods.service.ts` 的排序是 `orderBy: [{ isVerified: 'desc' }, { id: 'asc' }]`，
   即「先按是否认证、再按入库顺序」。搜「鸡」命中几十条时，排在前面的是**入库早的**，不是最像的。
2. **前端固定只取前 20 条**（`limit: 20, offset: 0`），接口返回了 `total` 但前端**不渲染总数、不提供「加载更多」**。
   用户既翻不到第 21 条，也**不知道还有更多**。

这直接打击 G1「记一餐足够便宜」：**搜不到 → 记不下去 → 干脆不记**。
而成本是小的（一条排序规则 + 前端一个控件），收益是每次搜索都发生的。

### 🥉 第三优先（**已完成**）：**B2 · 周报可回看历史周** —— 能看任意一天、能看 30/365 天，唯独看不了上一周

> ✅ **已交付 `40a159d`**（`WeeklyReportView` 支持「上一周 / 下一周」+ `<input type="date">`；见 §5）。下列为交付前判断。

现在的时间维度覆盖是**缺一块的**：

| 维度 | 现状 |
| --- | --- |
| 某一天 | ✅ 可跳任意历史日（N2） |
| 一周 | ⚠️ **锁死在本周** —— `WeeklyReportView` 的 `endDate` 恒为 `todayKey()` |
| 30 / 365 天 | ✅ 阶段回顾（R11.3） |

而周维度恰恰是 PRD 定义的核心维度（§6 第 10 行「周报：周维度摄入/缺口/体重/习惯汇总」）。
更关键的是：**后端 `GET /report/weekly?endDate=` 早就支持任意日期**，UI 只是没用 —— 成本几乎为零。

> 若只做一件：**做 A1**。它是唯一一个「产品已经承诺、用户已经照做、但结果不成立」的项。
>
> ⚠️ **回填提示**：A1 已交付 `9f484a0`（见 §5），此「若只做一件」的结论**已失效**，仅存为当时的判断记录。

## 4. C 类：基于产品定位新发现的机会点

### C1 · 快速加卡与库内食物重名时的温和提示（1773 条后**新出现**的问题）

| 字段 | 内容 |
| --- | --- |
| **一句话** | 快速加卡手填的食物名若库里已有，温和地问一句「库里已经有了，用它吗？」 |
| **用户价值** | 食物库从 443 → **1773 条**后，用户手填「番茄炒蛋」时**库里大概率已经有了**。现状是静默创建一条重复的自定义食物，带来三个后果：① 库被个人重复数据污染；② 手填热量往往不如库内准确；③ 常吃榜与多样性计数出现「同物两名」，统计被稀释 |
| **优先级** | **P1** |
| **大致成本** | **小→中**（复用现有 `/foods?q=` 做同名/近名检测 + 一个确认步骤） |
| **依赖项** | 无 |
| **风险 / 注意（关键）** | ① 这是**提供选择，不是纠正错误** —— 措辞必须是「库里已经有「番茄炒蛋」了，用它吗？也可以继续用你填的」，**默认尊重用户的选择**，禁止「你填错了」「检测到重复」；② **不得阻断**快速加卡（G1 优先），一键可跳过；③ 只对**同名或高度近似**触发，不做模糊轰炸 |

### C3 · 「和昨天一样」——一键复制当日餐次

| 字段 | 内容 |
