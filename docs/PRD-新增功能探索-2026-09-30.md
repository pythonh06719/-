### 0.2 本轮摸索出的「真正空白」在哪里（一句话结论）

## 2. 候选详述

### D-1 · 上次份量记忆（「你上次记的是 200g」）

> 📌 **2026-10-02：已交付**（`287915f` + `bd14d39`）—— 本节「取证」栏的「无任何按用户记忆份量的实现」为立项前快照，已过时，原样保留。

| 字段 | 内容 |
| --- | --- |
| **一句话** | 选中一个食物准备记录时，默认份量**优先用你上次记这个食物用过的克数/份量单位**，没有历史才回落到食物库的通用默认。 |
| **解决的真实痛点** | **场景**：早餐固定「豆浆 + 鸡蛋 + 包子」，午餐办公楼下「黄焖鸡（大份）」。每次选中食物，份量都会被重置成食物库的通用默认值，用户**每次都得多点一下 / 填一次克数**。G1 承诺「≤3 次点击记一餐」，但那是对**第一次记某个食物**划算；对**天天吃的那几样**，第 2 次点击（选份量）永远省不下来 —— 单次摩擦小，乘以「每天 × 每餐 × 半年」就不小，而且恰好落在**最高频**的食物上。 |
| **取证** | ① 选中食物即重置为通用默认：`apps/web/src/pages/diary/MealComposer.tsx:519-525` 的 `chooseFood()` 调 `resolveDefaultServing(food)`；② 该函数定义在 `apps/web/src/pages/diary/meal-utils.ts:25-38`，注释明写「取食物的默认份量克数：优先 `isDefault` 单位，其次首个单位，最后 100g」，**完全不参考用户历史**；③ 全仓 grep `lastPortion｜lastGrams｜previousPortion｜上次份量｜默认份量`（`apps/web/src` + `apps/api/src` + `packages/core/src`）**仅命中 `defaultPortion` 相关注释**，**无任何「按用户记忆份量」的实现**。 |
| **产品形态建议** | 数据源**不需要新表** —— `meal_logs` 每条已存 `grams` / `servingUnit`（`apps/api/prisma/schema.prisma:256-258`），且已有索引 `@@index([userId, foodItemId])`（`schema.prisma:278`）。实现二选一：<br>① **服务端派生**（推荐）：查询「本人该食物最近一条记录的 grams + servingUnit」，随搜索结果一起返回，**跨端一致**（web 与小程序同源）；<br>② **本地缓存**（同 C2「档位记忆」口径，见 `/why-numbers` 的 `why-tool-memory`，`apps/web/src/pages/why-numbers/WhyNumbersPage.tsx:1108-1163`）。<br>UI：份量区出现一行中性说明「上次记的是 200g」，用户可直接确认或修改。 |
| **与调性的契合度** | ★★★。**正确做法**：纯摩擦削减，把「上次的选择」摆出来供确认，**不产生任何新数字、新评价**。<br>⛔ **明确反对的做法**：① 把它做成「**推荐份量**」（一旦叫推荐，就是在替用户决定吃多少）；② 用「你上次吃多了/吃少了」之类措辞作对比；③ 因有记忆值而**自动跳过份量确认**（会让热量估算失真，触碰 G2 红线）。 |
| **风险与规避** | **低**。① 无历史 → 回落 `resolveDefaultServing`，行为与现状完全一致；② 用户改了单位时以**克数**为准（避免单位换算漂移）；③ 记忆值**只作为默认填值**，绝不参与任何统计口径（不污染 R11.5/R11.7）；④ 需在 `/why-numbers` 加一句「这个默认份量是怎么来的」（NFR-11）。 |
| **优先级建议** | **P1**。它是本轮**唯一直接命中 G1** 的项，且打击的是**最高频**的记录动作。 |
| **大致成本** | **小**。api：一个「本人该食物最近一条记录」查询（索引已就绪）或并入既有搜索响应的字段；web：`chooseFood` 优先用记忆值 + 一行说明。 |
| **是否与现有功能重复** | **不重复。** ① R3.4「最近吃过 / 收藏」给的是**食物条目**，选中后份量仍回到通用默认；② R11.5「我的常吃榜」给的是**名称 + 出现天数**，不含份量；③ R3.9「套餐模板」是**跨天复用的组合**，不记忆**单品份量**；④ B3「可改份量」（已交付 `809c6ff`）是**事后纠错**，本项是**事前默认**，方向相反、互补。 |

### D-2 · 重复记录温和提示（防当天热量被静默翻倍）

> 📌 **2026-10-02：已交付**（`24a7c3c`，默认放行）—— 本节「取证」栏的「防重复记录从未实现」为立项前快照，已过时，原样保留。

| 字段 | 内容 |
| --- | --- |
| **一句话** | 当你要记的这条食物**当天同一餐次已经记过一次**时，温和问一句「这餐好像已经有它了，再加一份，还是看看已记的？」，**默认不阻断**。 |
| **解决的真实痛点** | **场景**：午饭时手滑点了两次「米饭」；或先用套餐一键添加、又手动加了一次「鸡腿」；或记完一餐后误触重复提交。结果是**当天热量静默翻倍**，用户直到看进度环发现数字不对，还得**一餐一餐翻回去找是哪条重复**。这类误记直接破坏 G2「数字可信」——用户一旦发现数字会无缘无故翻倍，就会开始怀疑所有数字。 |

| **产品形态建议** | **沿用 C1「同名温和提示」的交互范式**（`MealComposer.tsx:1130-1159`：「库里已经有了……用它吗？也可以继续用你填的」）：提交前若命中「同日 + 同 mealType + 同 foodItemId（或同名）」，给一句提示 + 两个选项：**「再加一份」（放行）** / **「看看已记的」（定位到那条）**。判定口径（同名归一）放入 `@qsh/core` 纯函数单一真源。 |
| **与调性的契合度** | ★★★。**正确做法**：**提供选择，不是纠正错误** —— 真吃两份是合法的，所以默认放行、一键可跳过。<br>⛔ **明确反对的做法**：① 写成「检测到重复记录」「你是不是记错了」（指责）；② **拒绝提交**（真吃两份的合法场景被冤枉）；③ 用红色 / 警示语义；④ 对套餐添加的多个条目逐条弹提示（会变成轰炸）。 |

| **优先级建议** | **P2**。频率低于 D-1，但每次触发都直接救一次数据可信度。 |
| **大致成本** | **小**。前端提交前查一次当日该餐记录（可复用 `/meals?date=` 已有返回）+ core 纯函数判定 + 单测。**无后端新增接口**（若走前端判定）。 |
| **是否与现有功能重复** | **不重复。** C1「快速加卡重名提示」防的是**建食物条目**时的库内同名（污染 `food_items`、稀释统计）；本项防的是**记一餐**时的当天重复（污染 `meal_logs`、让热量翻倍）。对象（food_items vs meal_logs）与后果（库脏 vs 数字错）都不同。 |

### D-3 · 体重单位「斤」切换

> 📌 **2026-10-02：已交付**（`5d73c1d` + `1f9b07b` / `c1da861` / `fbb11b7` 口径收敛）—— 本节「取证」栏的「全站只认公斤、体重单位从未支持」为立项前快照，已过时，原样保留。

| 字段 | 内容 |
| --- | --- |
| **一句话** | 在设置里加一个**体重单位**偏好：**公斤 / 斤**（1 斤 = 0.5 kg）。内部存储、计算、导出**一律仍用 kg**，只在**展示层**换算。 |
| **解决的真实痛点** | **场景**：中文生活里，很多人（包括经常自用这台 App 的用户）报体重习惯说「我今天 138 斤」。但产品全站只有「公斤」—— 称完体重想核对「我今天到底几斤」，要么心算 ×2，要么每次看着 `69.0 kg` 自己在脑子里换算。对一个把「**中文生活化**」写进差异化三件套的产品，这是**每天都要跨的一道换算坎**，且是纯粹的本地化缺口。 |
| **取证** | ① 体重格式化只有 kg：`apps/web/src/lib/format.ts:110-112` 的 `formatWeight(kg)` 直接 `kg.toFixed(1)`；`Sparkline.tsx:82`、`WeightChart.tsx:409` 的 aria 文案硬编码「公斤」；② 单位偏好只有能量一条轴：`apps/web/src/lib/units.ts` 只处理 `kcal / kJ`（`:3, :7, :35, :38`），**没有体重单位**；③ 全仓 grep `斤`（`apps/web/src` + `apps/api/src` + `packages/core/src` + `packages/shared-types/src`，排除测试）**零命中属于本产品的「斤」用法**（仅 `公斤` 出现在少数注释/aria）—— 即「斤」从未被支持。 |
| **产品形态建议** | 与 R2.11（kcal/kJ 全局切换）**做成交互对称的一条偏好**，放在 `/profile`（`ProfilePage` / `GoalSettingsCard` 附近）。换算函数进 `@qsh/core`（`1 斤 = 0.5 kg`，纯函数 + 单测），前端只做展示换算。**覆盖范围要一次到位**：体重输入框、记录列表、趋势图纵轴、7 日均线读数、目标进度、预测曲线、平台期卡片、`/why-numbers` 里所有体重数字。 |
| **与调性的契合度** | ★★★。**正确做法**：纯展示口径本地化，让用户用自己习惯的单位看自己的数字。<br>⛔ **明确反对的做法**：① 切换单位时**改动内部存储或导出**（导出必须保持 kg，否则「换了单位后备份对不上」，破坏数据主权）；② 斤、kg 来回换算产生**取整漂移**导致同一条记录在两个页面显示不一致；③ 借单位切换引入任何「标准体重 / 达标体重」口径。 |
| **风险与规避** | **中**（**风险全在"覆盖面"**）。规避：① **唯一真源**是核心层换算函数，前端不重写公式；② 必须**穷举搜一遍所有出现体重数字的角落**（图/表/输入/文案/aria），否则会出现「一半斤一半公斤」的割裂感；③ 输入侧的斤 → 存库仍转回 kg（写路径不变）；④ 在 `/why-numbers` 说明换算基准。 |
| **优先级建议** | **P2**。不是"救命"功能，但对**中文生活化**这条卖点是"最实在、每天都能感知"的一刀，成本可控。 |

### D-4 ·「历史上的今天」（一年 / 一月前的今天）

| 字段 | 内容 |
| --- | --- |
| **一句话** | 进入看板时，若恰好有可对照的历史，轻量呈现「**一年前的今天** / **一个月前的今天**你记了什么」，把记忆**主动**带到用户面前。 |
| **解决的真实痛点** | **场景**：单人长期记录，数据越攒越多，却**几乎不会主动回头翻**（没有由头，也没有人提醒）。第 7 个月打开 App，如果能看到「5 个月前的今天：你刚开始记录，体重 72.4kg；那天你记了 2 餐」，那正是**付出感**最自然的兑现 —— 而且**用户不需要付出任何操作**，产品替他找到了那个「值得回看的日期」。这对单人自用场景尤其重要：**没有观众，记忆只能自己给自己**。 |
| **取证** | 全仓 grep `历史上的今天｜去年今天｜一年前的今天｜onThisDay｜往日`（`apps/web/src` + `apps/api/src`）**零命中** —— 该能力从未实现。现有回看全部是「用户主动指定日期/区间」：`DiaryPage` 的日期跳转、`WeeklyReportView` 的周切换、`PeriodReportView` 的 30/365 天档。 |
| **产品形态建议** | 在两处之一轻量出现：`/dashboard` 底部，或 `/report` 一句引子。**仅当历史里有对应日期附近的数据时才渲染**（否则整块隐藏，不留空卡）。卡片内容为**纯事实**：某年/某月的今天，体重多少、记了几餐、有没有「体重之外的变化」、当天一句备注；点击 → 复用 N2 一日档案。 |
| **与调性的契合度** | ★★★。**正确做法**：纯回看、非评价；是「留住 = 被看见」的正向回归，与 c-1（足迹日历）属同一主题的不同机制。<br>⛔ **明确反对的做法**：① **禁止做"对比"**（如「你比那时胖了/瘦了 X kg」—— 把记忆变成评判）；② 禁止做成「纪念日 / 连续 N 天成就」（游戏化）；③ 禁止主动推送 / 弹窗（NFR-10，**仅进入时展示**）；④ 禁止"你当时很努力"之类的煽情叙事。 |
| **风险与规避** | **低→中**。① 历史不足 → **整块隐藏**；② 措辞中性（只说事实，不褒不贬，不出现「进步/退步/坚持了」）；③ 时区对齐复用既有 `daykey`；④ 若涉及"一年前"，需处理闰年/2-29 边界；⑤ 不产生新数字 → 是否需 `/why-numbers` 由架构师定（若只呈现已有数字，不新增口径）。 |
| **优先级建议** | **P2**。价值高、成本低，但**触发频率低**（每天一次机会），排在 D-1 / D-2 之后更合理。 |
| **大致成本** | **小**。复用 N2 的按日聚合；后端只需一个「按指定日期取当日摘要」的查询（若 N2 已具备则直接复用），前端一张条件渲染卡片。 |
| **是否与现有功能重复** | **不重复（机制差异）**。① C-1「记录足迹日历」是**空间维度**：一张月历网格，用户**主动翻**；本项是**时间复现**：把「今天」这个坐标**映射到过去**，是**被动唤起记忆**。② N2「一日档案」是**入口**（要先知道日期才能去）；本项是**系统自动带给你一个日期**。③ R11.3 阶段回顾是**聚合量**，不是某一天的复现。 |

| **是否与现有功能重复** | **不重复。** ① N3「体重波动归因」是**单日、针对体重**；② R11.3「阶段回顾」是**累计量与多样性**；③ 本项是**时间分布**（周几 / 时段）的自我观察，是既有 report 维度里**从未有过的新轴**。 |

## 5. 推荐排序与理由

| 排名 | 候选 | 一句话理由 |
| --- | --- | --- |
| 🥇 **1** | **D-1 上次份量记忆** | **唯一直接命中 G1** 的一条，且打击的是**每天都发生**的最高频动作；成本小、零新表、索引已就绪。 |
| 🥈 **2** | **D-3 体重单位「斤」** | **中文生活化**最实在的一刀 —— 每天都跨的换算坎，纯展示层，与既有 kcal/kJ 交互对称。 |
| 🥉 **3** | **D-2 重复记录温和提示** | **保护 G2「数字可信」**，成本极小（前端判定即可），触发一次就救一次。 |
| 4 | **D-5 我什么时候吃过它** | 长期用户"检索自己的历史"的实感，索引已就绪，成本小→中。 |
| 5 | **D-4「历史上的今天」** | **付出感的被动兑现** —— 不需用户操作就把记忆带回眼前，成本小。 |
| 6 | **D-6 周内 / 时段节奏洞察** | 新的观察维度，但**红线风险最高**（易滑向因果/评判），价值/风险比最低。 |

> **建议评估顺序**：**D-1（必做，成本最小收益最直接）→ D-3 / D-2（一个管口径、一个管数据可信）→ D-5 / D-4（长期回看，按意愿取舍）→ D-6（风险最高，最后评估，也可只保留观察）。**
