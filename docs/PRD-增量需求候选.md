## 0. 分析前提

### 0.1 这一轮要回答的问题

「还能新增什么功能」——重点是**候选清单 + 价值判断**。当前主要使用者是用户本人（单人长期记录），
因此评估权重明显偏向**自用场景**：

| 自用场景的真实诉求 | 对应的功能方向 |
| --- | --- |
| 回头看自己的历史（3 个月前那天吃了什么、状态如何） | 一日档案、阶段回顾 |
| 体重卡住时不想放弃（**单人长期最大的流失点**） | 平台期解释、波动归因 |
| 减到目标之后怎么办 | 维持模式 |
| 数据的沉淀感（我的记录是有价值的） | 阶段回顾、常吃榜、非体重胜利 |
| 数据不能丢（一个人没有其他人帮你留底） | 自动备份 |

### 0.2 硬性边界（候选必须守住）

1. **无负罪感**：不指责、不制造焦虑、不用红色恐吓语义。
2. **可解释**：每个数字可查来源与算法（`/why-numbers`）。
3. **生活化**：外卖 / 零食 / 聚餐 / 饮品是核心场景。
4. **不越界**：不做医疗建议、不鼓励极端节食、不做付费墙。
5. **不自相矛盾**：不重复需求池 R1.x~R10.x 已覆盖的能力。

### 0.3 已在需求池中、本轮**刻意排除**的方向（避免重复提案）

| 方向 | 已被哪条覆盖 |
| --- | --- |

## 2. 候选详述

### N1 · 平台期说明（Why is nothing changing?）

| 字段 | 内容 |
| --- | --- |
| **一句话** | 当体重连续 N 周（建议 3 周）无明显变化时，主动给出一段解释 + 一个「看 4 周斜率」的视角，而不是让用户自己怀疑人生。 |
| **解决的真实痛点** | 单人长期记录**最真实的放弃点**。用户已经坚持 2 个月，某天开始连续 3 周体重不动——此时产品若只是照常显示一条平线，用户的结论会是「方法没用 / 我不行」，然后停用。这是自用场景下**留存的第一杀手**，比任何新功能都重要。 |
| **产品形态建议** | 在 `/weight` 顶部出现一张温和卡片：识别到平台期 → 说明「体重在一段时间里停下来很常见，通常和水分、饮食记录精度、身体适应有关」→ 展示 4 周移动平均斜率（比 7 日更慢但更稳）→ 给一个可选动作（检查一下记录是否完整 / 把目标期限放宽一点）。**不做**「加大缺口」类建议。 |
| **与调性的契合度** | ★★★ **完美契合三条差异化**：① 无负罪感——把「停滞」重新定义为「正常阶段」而非失败；② 可解释——明确给出判定规则（连续 N 周、斜率阈值、用哪条均线）并可在 `/why-numbers` 查到；③ 生活化——落在真实的减重节奏上。 |
| **风险与规避** | 低风险。唯一要避免的是给出「那就吃更少 / 动更多」的处方（会滑向鼓励极端节食）。建议动作只能是**记录完整性**和**放宽期限**两类。 |
| **优先级建议** | **P0** —— 理由：它不是「锦上添花」，而是直接服务于 G3「坚持不需要意志力」。对单人长期使用，它的价值高于任何新页面。 |
| **大致成本** | **中**。core（`weight/` 下新增平台期判定 + 4 周斜率，纯函数可测）+ web（`/weight` 卡片与文案）。不需要新的 DB 表，复用 `weight_logs`。 |

### N2 · 一日档案（回到任意历史一天）

| 字段 | 内容 |
| --- | --- |
| **一句话** | 提供日历入口（或从体重曲线点某个点）直接跳到任意历史日期，一屏内看到那天的饮食、体重、饮水、习惯、备注。 |
| **解决的真实痛点** | `/diary` 只能用「前一天」按钮逐日回退——想看 3 个月前的某一天要点几十次，实际上等于**看不了**。而「回头看自己的历史」正是自用场景的核心乐趣：那天聚餐吃了什么？那时候体重多少？当时备注写了什么？目前这些信息分散在 `/diary`、`/weight`、`/habits` 三个页面，且无法对齐到同一天。 |
| **产品形态建议** | 新增 `/day/:date`（或在 `/diary` 上加日历入口）。一屏 = 日期 + 当日总摄入 + 体重（含当日备注）+ 饮水 + 习惯完成情况 + 逐餐列表。**只读回看**，补录沿用现有入口。 |
| **与调性的契合度** | ★★★。纯回看、不评价、不打分；历史某天没记录就显示「这天没有记录，也没关系」。完全守得住无负罪感。 |
| **风险与规避** | 低。要注意：**不要**在回看页做「这天超标了 X kcal」的追溯性评判——历史日只呈现事实，不给结论。 |
| **优先级建议** | **P1**。它是「数据沉淀感」的地基——N5（阶段回顾）与 N6（非体重胜利）都依赖「能方便地翻到某一天」。建议先做 N2 再做 N5。 |
| **大致成本** | **中**。api（一个按日期聚合的只读接口，复用现有 meals/weights/water/habits 查询）+ web（日历选择器 + 一日档案页）。无需新表。 |

### N3 · 体重波动归因（上涨时给原因，不给指责）

| 字段 | 内容 |
| --- | --- |
| **一句话** | 体重比昨日上涨时，除了「波动很正常，看趋势就好」，再给一句**可能的原因**——基于已有数据（昨天摄入偏高 / 昨天聚餐模式被用过 / 昨天没运动 / 处在生理期 / 最近睡眠少）。 |
| **解决的真实痛点** | S3 场景（晚上称重比昨天重 0.8kg）现在是靠一句通用安慰兜底。单人长期记录后，用户其实**有能力**知道原因——因为数据就在库里。通用安慰用 20 次之后会变成空话；能说出「昨天那顿火锅盐分不少，多留 1kg 水分很常见」，说服力完全不同。 |
| **产品形态建议** | 在 `/weight` 当日记录下方展示 1~2 条**候选原因**（不是结论）：「昨天摄入比平时高一些」「昨天用了聚餐模式」「最近 3 天平均睡眠偏少」。措辞一律用「可能」「通常」「有可能」。 |
| **与调性的契合度** | ★★★。这是**可解释性**与**无负罪感**的交汇点：把「我变重了 = 我做错了」改写成「我变重了 = 有个可以解释的原因」。 |
| **风险与规避** | **中等，需注意两点**：<br>① **绝不能写成因果断言**——只能是相关提示，且必须可关闭；<br>② 若引入**生理周期**数据，属敏感健康信息（PRD Q12 已将 `conditions` 列为敏感字段）：必须**显式二次同意**才采集、不预测排卵/经期、不给出任何健康结论、导出默认排除、一键删除。建议**一期只用已有数据（摄入/运动/聚餐/习惯）做归因，生理期作为后续可选项**。 |
| **优先级建议** | **P1**。成本可控、收益直接，且能复用 N2 的按日聚合能力。 |
| **大致成本** | **小→中**。先用已有数据做规则版（core 纯函数 + web 展示）成本为**小**；若后续加生理期则需要 DB 字段与隐私设计，升为**中**。 |

### N4 · 目标达成后的维持模式

| 字段 | 内容 |
| --- | --- |
| **一句话** | 当体重达到目标体重后，产品从「减重模式」切换为「维持模式」：缺口归零、建议摄入回到 TDEE、页面语言从「距离目标还有 X」变成「保持在 X 附近就很好」。 |
| **解决的真实痛点** | **这是需求池的真实空白。** R2.7 taper 只覆盖「接近目标时收窄缺口」，但**到达目标之后**怎么办，PRD 完全没写。而单人长期使用必然走到这一天——届时产品若还在催用户继续制造缺口，既无意义又与「不极端」的定位冲突。 |
| **产品形态建议** | ① 引擎层：目标达成（体重 ≤ 目标体重）时进入 `maintenance` 状态，缺口 0、建议摄入 = TDEE；<br>② UI：看板不再显示「还差 X kg」，改为「维持在 X kg 附近」+ 一句认可；<br>③ 允许用户在「维持」与「设定新目标」之间自选，**不主动劝用户继续减**。 |
| **与调性的契合度** | ★★★。**高度契合**——它主动阻止产品把用户推向更极端的目标，是「不极端」这条边界的正面落地。 |
| **风险与规避** | 低。要避免的是「达成后立刻推送新目标」的惯性设计；必须默认停在维持状态。 |
| **优先级建议** | **P1**（若用户当前距目标尚远，可降为 P2；但它属于**迟早要做**的结构性空白）。<br>**补充发现**：引擎目前对「已达目标」的处理是**自然退化**而非崩溃——`deriveWeeklyLossKg` 推导为 0 → 缺口 0 → 摄入 = TDEE → `etaWeeks = null`，不会抛错。所以这是 **UX/状态空白，不是引擎缺陷**，改动可控。 |
| **大致成本** | **小→中**。core（新增维持态判定，纯函数）+ api（目标状态字段）+ web（文案与看板分支）。若不动 DB，仅靠体重与目标值实时判定，成本为**小**。 |

### N5 · 我的这段时间（阶段回顾）

| 字段 | 内容 |
| --- | --- |
| **一句话** | 月度 / 年度回顾页：记录了多少天、体重变化了多少、最常吃的几样东西、坚持得最稳的习惯、用过几次生活化工具。 |
| **解决的真实痛点** | 自用场景下的**沉淀感与动力**。每天的记录是碎的，一年下来应该有一样东西能把它们串起来——这也是各大 App 年度账单让人愿意打开的原因。对单人用户，「我已经记录了 143 天」本身就是最强的坚持理由。 |
| **产品形态建议** | 在 `/report` 增加「这段时间」标签页，按 30 天 / 365 天切换，输出 5~6 个**中性或正向**的统计量。严禁出现「你失败了 N 次」「最长断签」这类负向指标。 |
| **与调性的契合度** | ★★☆。**部分契合，措辞必须把关**：回顾天然带有「评价」意味，容易滑向打分。<br>**守住的写法**：只呈现**累计量与多样性**（记录天数、吃过的食物种类数、坚持最久的习惯），不呈现**缺失量与失败量**。<br>⚠️ **不建议放「连续记录最长纪录」**——那会把「历史最佳」变成一种压力（PRD §7 已明确「连续打卡 30 天，不能断！」是反例）。 |
| **风险与规避** | 中等（措辞风险）。规避方式：所有指标先过一遍「这是事实还是评判」，评判类一律不做。 |
| **优先级建议** | **P1**（但**建议排在 N2 之后**——没有方便的按日回看，回顾页就是无根之木）。 |
| **大致成本** | **中**。api（聚合查询，可复用 `/report` 现有聚合）+ web（回顾页与可视化）。无需新表，但聚合 SQL/查询较多。 |

### N6 · 体重之外的变化（非体重胜利）

| 字段 | 内容 |
| --- | --- |
| **一句话** | 一个轻量入口，随手记一条与数字无关的正向变化：「今天爬楼不喘了」「裤子松了一圈」「下午没犯困」。 |
| **解决的真实痛点** | 平台期（N1）时，体重给不了正反馈，人就容易放弃。而真实生活里的改善往往先于体重出现——只是没人帮你记下来。自用场景下，攒了 20 条这样的记录，回头翻（配合 N2）是非常强的动力来源。 |
| **产品形态建议** | 极轻量：一句话输入 + 日期，列表展示。可挂在 `/weight` 底部（「体重之外，也有一些变化」），与平台期卡片形成互补。 |
| **与调性的契合度** | ★★★。直接把注意力从「数字」转移到「生活」，是「不节食、不极端」定位的最佳注脚。 |
| **风险与规避** | 低。唯一注意：不要做成「成就系统 / 徽章 / 等级」（游戏化会反向制造完成压力）。 |
| **优先级建议** | **P2**（成本低、契合度高，但依赖 N1/N2 先落地才有回看价值）。 |
| **大致成本** | **小**。新增一张表（或复用 `habit_definitions` 思路）+ 一个页面区块。 |

### N7 · 我的常吃榜 / 我的常点

| 字段 | 内容 |
| --- | --- |
| **一句话** | 自动统计你最常吃的食物与最常点的外卖品类，在搜索时置顶，并在阶段回顾里展示。 |
| **解决的真实痛点** | 记录 3 个月后，用户的真实饮食结构其实很固定（可能就反复吃那 30 样）。但目前每次记录都要重新搜索一遍——R3.4 的「收藏」和「最近吃过」能缓解，但**需要用户手动维护**。自动统计的常吃榜是零维护成本的加速。 |
| **产品形态建议** | 搜索框空态时展示「你常吃的」（按近 90 天频次自动排序）；`/tools` 外卖换算器记住你常用的品类与档位。 |
| **与调性的契合度** | ★★☆。中性偏正向。⚠️ **注意**：若展示成「你喝了 87 杯奶茶」并带负面暗示，就违背了无负罪感——**只呈现频次，不做健康评判**（正确写法：「这 90 天里，奶茶出现了 12 次」；错误写法：「你摄入了过多糖分」）。 |
| **风险与规避** | 低（措辞风险）。规避：只做频次统计与快捷入口，不做任何营养评判。 |
| **优先级建议** | **P2**。属于效率优化，不是留存刚需。 |
| **大致成本** | **小→中**。api 侧一个按 `meal_logs` 聚合的统计查询（成本小），web 侧搜索置顶 + 回顾展示（成本小）；若要做「常点外卖档位记忆」则升为**中**。 |

### N8 · 自动定期备份 + 数据健康自检

| 字段 | 内容 |
| --- | --- |
| **一句话** | 每月自动生成一份本地备份（或提示手动导出一次），并在「长期未备份」「数据异常（如体重记录出现明显离群值）」时温和提示。 |
| **解决的真实痛点** | **自用场景特有**：一个人用，没有团队帮你做备份。R10.1 已提供「一键导出」，但**前提是用户想得起来点**。一年的体重与饮食记录如果因为换设备/误删而丢失，是不可恢复的——而这类数据越久越有价值。 |
| **产品形态建议** | 在 `/settings/data` 增加「上次备份：X 天前」+ 一个「现在备份」按钮；超过 30 天未备份时，在设置页显示一行温和提示（**不弹窗、不推送**，遵守 NFR-10）。 |
| **与调性的契合度** | ★★★。完全契合「数据真正属于我」（US-18）——把纸面上的数据主权变成实际发生的事。 |
| **风险与规避** | 低。⚠️ 注意：自动备份若走云端会引入隐私与成本问题，**建议只做本地下载/IndexedDB 快照**，不上传。 |
| **优先级建议** | **P2**（成本低但需要用户确认备份方式偏好）。 |
| **大致成本** | **小→中**。纯本地方案（定时提示 + 复用现有导出）为**小**；若要做真正的自动快照与恢复则为**中**。 |

### N9 · 身体围度记录

| 字段 | 内容 |
| --- | --- |
| **一句话** | 除体重外，记录腰围 / 臀围 / 大腿围等围度，作为体重平台期的替代进步信号。 |
| **解决的真实痛点** | 真实存在：体重不动但体围在变，是减脂期的常见现象。只盯体重一个数字，容易在平台期误判为「没效果」。 |
| **产品形态建议** | 若做：独立记录 + 自己的趋势线，**只显示变化量，不给标准值、不给「正常范围」、不做身材评价**。 |
| **与调性的契合度** | **⛔ 有风险，需规避设计**：围度记录天然靠近「身材评价」，容易滑向焦虑源（尤其对有饮食障碍倾向的用户）。<br>**要守住必须同时满足**：① 不给任何参考区间/标准值；② 不与体重合并成「综合评分」；③ 可完全关闭；④ 不主动提醒测量。 |
| **风险与规避** | **中等偏高**。规避方式见上；若无法满足 ①②③④，**建议直接不做**。 |
| **优先级建议** | **P2**（且建议**排在 N1/N6 之后**——用「体重之外的变化」这种轻量方式先验证用户对非体重指标的真实需求，再决定是否投入围度这种重功能）。 |
| **大致成本** | **中**。新表 + 独立趋势图 + 设置项。 |

### N10 · 饮食多样性计数

| 字段 | 内容 |
| --- | --- |
| **一句话** | 「这周吃到了 23 种不同的食物」——只做种类计数，不做营养评分。 |
| **解决的真实痛点** | 长期自用容易陷入「每天吃一样的东西」（因为记录成本低）。多样性计数是一个温和的提醒，且回顾时很有趣。 |
| **产品形态建议** | 在 `/report` 周报里加一行计数；点击可展开这周吃过的食物清单。 |
| **与调性的契合度** | ★★☆。<br>✅ 正确做法：**计数 + 罗列**（「这周吃了 23 种食物」）。<br>⛔ **明确反对**：做成「营养均衡度评分 / A-F 等级 / 打分条」——一旦出现分数，就变成评判，直接违背无负罪感（参考 PRD §7 对恐吓式文案的禁令）。 |
| **风险与规避** | 低（只要不评分）。 |
| **优先级建议** | **P2**。 |
| **大致成本** | **小**。复用 `meal_logs` 做去重计数即可。 |

## 3. 最推荐的前 3 个

### 🥇 第一优先：N1 平台期说明

**理由**：它是这份清单里**唯一直接影响「会不会停用」**的功能。

单人长期记录的流失曲线，最陡的那一刀一定出现在「坚持了很久但体重不动」的时候。此时产品若只显示一条平线，
用户得到的潜台词是「你的努力没用」——这与 G3「坚持不需要意志力」完全相反。而 N1 的成本并不高
（core 纯函数判定 + 一张文案卡片，无新表），却把产品从「记录工具」推进到「陪你扛过平台期的工具」。

**建议作为本轮唯一的 P0 候选。**

### 🥈 第二优先：N4 目标达成后的维持模式

**理由**：它是需求池里**真实存在的结构性空白**，而且迟早会撞上。

R2.7 taper 覆盖了「接近目标」，但**到达目标之后**PRD 一字未提。若不补，用户达成目标的那天，
产品还在催他继续制造缺口——既无意义，又直接违背「不极端」这条定位。补上它，产品才有一条完整的终点。

而且它的成本是**小**的：引擎对已达目标的处理本来就是自然退化（缺口 0、摄入 = TDEE、etaWeeks = null），
不会抛错——只需要补一层状态判定与一套文案。

### 🥉 第三优先：N2 一日档案

**理由**：它是「数据沉淀感」这条线的地基，且另外两个候选都依赖它。

- N5（阶段回顾）没有方便的按日回看，就是无根之木；
- N6（体重之外的变化）攒了记录却翻不到，价值大打折扣；
- 而当前 `/diary` 只能逐日点「前一天」——想看 3 个月前的某一天实际上等于看不了。

把它放在第三，是因为它**锦上添花但不救命**；做完 N1 和 N4，产品就没有「会让人停用」和「逻辑走不通」的问题了，
这时再做沉淀层，顺序最顺。

> 建议实施顺序：**N1 → N4 → N2 → (N3 / N5) → 其余按需**。

## 4. 明确不建议做 / 有风险的点

### 4.1 明确不建议做（违背定位）

| 方向 | 为什么不做 |
| --- | --- |
| **好友 / 排行榜 / 打卡 PK / 社区** | ① 当前是单人自用，社交功能零收益；② 排行榜是焦虑制造机，与无负罪感正面对冲；③ 引入他人数据带来隐私与合规成本。 |
| **断签挽回推送 / 未记录催办通知** | NFR-10 明令「不主动发用户未开启的通知」，PRD §7 把「今天还没记录，快去补上！」列为反例。 |
| **减肥挑战 / 打卡营 / 极端断食模式** | 落入「鼓励极端节食」红线；R8.x 已把断食做成默认关闭 + 内容警告 + 「这不适合我」一级按钮，不应再加码。 |
| **营养评分 / A-F 等级 / 均衡度打分** | 一旦出现分数就是评判，直接违背无负罪感（N10 若做，只能计数不能打分）。 |
| **代餐 / 减肥药 / 补充剂推荐** | 涉及医疗与健康商业，越界。 |
| **付费墙 / 会员专属营养素** | R4.3 明确「作为免费差异化卖点，不做付费墙」。 |
| **让 AI 直接输出热量数字** | PRD 明令：AI 只返回食物名称与数量，热量必须由食物库匹配（R3.7 / NFR-6）。 |

### 4.2 有风险、若要必须做规避的功能

| 功能 | 风险 | 规避方式（必须全部满足） |
| --- | --- | --- |
| **N3 中的生理周期追踪** | ① 敏感健康信息；② 可能滑向健康建议 | 显式二次同意才采集；不预测排卵/经期；不给任何健康结论；导出默认排除；一键清除。 **建议一期不做**，只用已有数据（摄入/运动/聚餐/习惯）归因。 |
| **N9 身体围度记录** | 靠近身材评价，易成焦虑源 | 给标准值 ❌；与体重合成评分 ❌；必须可完全关闭；不主动提醒测量。四条缺一则不做的。 |
| **N5 阶段回顾** | 回顾天然带评价意味 | 只呈现累计量与多样性，**不呈现缺失量与失败量**；不放「最长连续记录」（会变成压力，PRD §7 已把「不能断」列为反例）。 |
| **进度照片对比** | 身体形象焦虑 + 照片隐私 | 本轮**不建议列入候选**。若将来要做：仅本地存储不上传、默认关闭、不评价、可一键清除，且优先级低于 N9。 |

### 4.3 一条通用提醒

所有新功能若要展示「数字」，都必须同步在 `/why-numbers` 补上来源与算法说明——
这是「可解释性」这条差异化的硬约束，N1/N3/N5/N10 都会在 `/why-numbers` 产生新增条目。
