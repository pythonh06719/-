# 「轻生活」产品需求文档（PRD）

| 项目信息 | 内容 |
| --- | --- |
| 文档语言 | 简体中文 |
| 产品名称 | 轻生活（项目代号 `qingshenghuo`） |
| 产品形态 | 移动端优先的响应式 Web / PWA（生活化减肥工具） |
| 建议技术栈 | React 18 + TypeScript + Vite + Tailwind CSS + PWA；后端 Node.js(NestJS) 或 Next.js 全栈；PostgreSQL（MVP 可用 SQLite）；图表 ECharts；部署 Docker Compose |
| 文档类型 | 简单 PRD（如需竞品分析请另行提出） |
| 版本 | v1.0（正式化首版） |
| 核心理念 | 不节食、不极端，把减肥融入日常生活 |

## 原始需求复述

为 20–45 岁、无专业营养知识、讨厌复杂操作与极端节食的普通上班族/学生，提供一款中文减肥网站。通过**科学卡路里计算**、**低门槛饮食记录（3 次点击记一餐）**、**习惯养成**与**数据可视化**，帮助用户可持续健康减重。差异化定位：以中式食物/外卖/奶茶零食为一等公民；明确采用「无负罪感设计」，无断签焦虑；微量营养素面板免费（竞品多为付费墙）。

## 1. 产品目标与成功指标

### 1.1 产品目标（3 个正交目标）

| # | 目标 | 说明 |
| --- | --- | --- |
| G1 | **记一餐足够便宜** | 把单餐记录的交互成本降到 ≤3 次点击/≤15 秒，让「记录」不再是负担 |
| G2 | **数字可信且安全** | 热量指标基于可溯源公式，强制安全下限与缺口上限，绝不给出危险建议 |
| G3 | **坚持不需要意志力** | 无负罪感文案与设计，断签无惩罚，用趋势而非单日波动评价用户 |

### 1.2 成功指标（MVP 上线后 4 周观测）

| 指标 | 目标值 | 衡量方式 |
| --- | --- | --- |
| 首次引导完成率 | ≥ 70% | 完成 `/onboarding` 问卷 / 进入引导页 |
| 新用户次日留存 | ≥ 35% | 第 2 日有登录或记录行为 |
| 单餐记录平均点击次数 | ≤ 3 | 埋点统计记录流程点击事件 |
| 记录接口 P95 响应 | < 300ms | 服务端监控 |
| 首屏可交互时间 | < 2s | 移动端 4G 环境 |
| 热量引擎单元测试通过率 | 100% | CI 强制门禁 |
| 7 日内 ≥3 天有记录的用户占比 | ≥ 40% | 埋点 |

> 说明：埋点仅使用**自托管的第一方统计**，**不得接入任何第三方行为分析 SDK**（见 NFR-7 与隐私承诺）。

## 2. 目标用户与使用场景

### 2.1 目标用户

- **主画像**：20–45 岁上班族/学生，BMI 偏高或希望减脂，无营养学背景。
- **次要画像**：孕期/哺乳期或慢病人群（**不作为减重目标人群**，仅需被安全提示拦截）。

### 2.2 核心场景

| # | 场景 | 用户诉求 |
| --- | --- | --- |
| S1 | 午餐点麻辣烫，边吃边记 | 不想搜十几样配料，只想快速估个热量并看到今天还剩多少 |
| S2 | 下午想喝一杯奶茶 | 想知道这杯多少卡，以及有没有更低卡的点法 |
| S3 | 晚上称重比昨天重了 0.8kg | 不要被红色警告吓到，想看趋势而非单日数字 |
| S4 | 出差一周没记录，回来想重新开始 | 不想看到「连续打卡 0 天」，不想被追责 |
| S5 | 想验证这个网站靠不靠谱 | 想知道热量公式出处，能否免注册先算一次 |
| S6 | 想换手机/退出 | 想把自己的全部数据导出带走并彻底删除 |

## 3. 用户故事（按角色分组，含验收标准）

### 3.1 未注册访客

- **US-01**：As a 访客，I want 在落地页免注册试用热量计算器，so that 我先确认产品有用再注册。
  - **验收**：`/` 页输入性别/年龄/身高/体重/活动量后立即返回 BMR、TDEE、建议摄入，无需登录；返回结果附「参考来源」入口与免责声明。

- **US-02**：As a 访客，I want 在落地页看到隐私承诺，so that 我放心地把体重数据交出去。
  - **验收**：`/` 页含「不出售数据、无广告 SDK、无第三方行为分析」文案与免责声明；不提供「一键登录即同意全部营销」类捆绑选项。

### 3.2 新用户

- **US-03**：As a 新用户，I want 用邮箱+验证码完成注册与引导，so that 快速拿到我的每日热量预算。
  - **验收**：注册支持邮箱验证码登录；`/onboarding` 收集性别、出生日期、身高、当前体重、目标体重、目标期限、活动量、饮食偏好、常见疾病；完成后跳转 `/dashboard` 并展示建议摄入。

- **US-04**：As a 新用户，I want 在引导前被告知适用边界，so that 我不会误用不适合我的方案。
  - **验收**：引导首屏展示**免责声明**（不提供医疗建议；孕期/哺乳期/疾病治疗期不建议使用热量缺口方案），需主动确认后方可继续。

- **US-05**：As a 新用户，I want 修改我的基础数据后系统自动重算，so that 我的预算始终正确。
  - **验收**：在 `/profile` 修改性别/身高/体重/目标/活动量后，BMR、TDEE、每日缺口、建议摄入、宏量营养素目标全部自动重算并即时生效。

### 3.3 记录型用户

- **US-06**：As a 上班族，I want 用「搜索 + 常见份量」在 3 次点击内记完一餐，so that 记录不打断我的生活。
  - **验收**：从 `/diary` 起，点击「+ 记录」→ 选定食物 → 选择份量并确认 = 3 次点击；记录后立刻反馈本餐热量与今日进度环。

- **US-07**：As a 用户，I want 对没有收录的食物快速加卡，so that 我不会因为搜不到就不记。
  - **验收**：快速加卡支持仅输入「名称 + 热量」即可入库，不强制填写三大营养素。

- **US-08**：As a 用户，I want 扫码录入包装食品，so that 不用手动查营养表。
  - **验收**：扫描条形码命中 Open Food Facts 时返回每 100g 营养并写入当日记录；未命中给出「未收录，是否快速加卡」引导。

- **US-09**：As a 用户，I want 用 AI 拍照/描述识别食物，so that 更省事。
  - **验收**：AI 仅返回**食物名称与数量**；热量数值必须由食物库匹配得出；AI 结果填入表单后**必须用户确认才入库**；AI 未配置时该入口隐藏或提示不可用，其余功能不受影响。

- **US-10**：As a 常吃固定早餐的用户，I want 把一餐存为套餐模板，so that 一键复用。
  - **验收**：可将当前餐次保存为模板并一键添加；模板修改不影响已生成的历史记录。

### 3.4 外卖 / 社交场景用户

- **US-11**：As a 用户，I want 用外卖换算器估算麻辣烫/黄焖鸡/轻食沙拉，so that 我不用逐样搜索。
  - **验收**：`/tools` 选择品类与份量档位后输出热量估算区间与「这样点更健康」替换建议。

- **US-12**：As a 用户，I want 知道一包薯片等于多少运动，so that 我建立直观认知但不被恐吓。
  - **验收**：零食救赎同时给出低卡替代与「吃掉它需要多少运动」换算（如「一包薯片 ≈ 快走 70 分钟」），文案不出现恐吓式措辞。

- **US-13**：As a 用户，I want 聚餐时一键估算并调整当天其他餐，so that 聚餐不再让我崩溃。
  - **验收**：聚餐模式支持火锅/烧烤/自助餐估算，并给出当天其余餐次的调整建议；不产生「超标警告」红色文案。

### 3.5 追踪与习惯用户

- **US-14**：As a 用户，I want 记录体重并看到带 7 日移动平均的趋势线，so that 我不被单日波动影响情绪。
  - **验收**：`/weight` 支持每日体重记录与备注；趋势图叠加 7 日移动平均线；体重上涨时展示「波动很正常，看趋势就好」。

- **US-15**：As a 用户，I want 运动消耗计入当日热量平衡，so that 我的预算更真实。
  - **验收**：选择运动项目与时长后，按 `消耗 = MET × 体重kg × 时长h` 计算并计入当日余额。

- **US-16**：As a 用户，I want 一键记录饮水，so that 打卡最简单的事也能坚持。
  - **验收**：首页水杯组件一键 +250ml；支持撤销上一条；可自定义每日目标。

- **US-17**：As a 用户，I want 断签后不被惩罚、被温柔召回，so that 我随时可以回来。
  - **验收**：习惯打卡展示当前连续/历史最佳；断签不发惩罚性提醒，文案为「休息一下没关系，随时回来」。

### 3.6 数据主权用户

- **US-18**：As a 用户，I want 一键导出全部数据为 JSON + CSV，so that 数据真正属于我。
  - **验收**：`/settings/data` 可导出 JSON（完整可恢复备份）与 CSV（格式见 §9.2）；导出包含体重、饮食、运动、习惯、饮水、设置。

- **US-19**：As a 用户，I want 导入历史数据、彻底删除账号，so that 我能自主掌控。
  - **验收**：支持 JSON 备份恢复与 CSV 模板批量导入历史体重；账号删除为**硬删除**（数据库真实移除，非标记删除）。

### 3.7 安全敏感用户

- **US-20**：As a 有慢病/孕产情况的用户，I want 被明确提示本产品不适用，so that 我不被误导。
  - **验收**：引导问卷中勾选孕期/哺乳期/疾病治疗期时，展示醒目安全提示并建议咨询专业医师；不提供「继续使用减重方案」的一键按钮。

- **US-21**：As a 使用 AI 助手的用户，I want 在被检测到高风险意图时得到固定就医建议，so that AI 不越界。
  - **验收**：检测到疾病诊断、停药、极端节食类意图时，固定回复就医建议，不给出具体医疗/用药意见。

## 5. 热量计算引擎字段契约（供架构师/工程师直接消费）

### 5.1 输入 `CalorieInput`

| 字段 | 类型 | 必填 | 说明 / 取值 |
| --- | --- | --- | --- |
| `gender` | `"male" \| "female"` | 是 | 用于 BMR 公式与安全下限 |
| `age` | `number` | 是 | 周岁，来自出生日期；校验 14–100 |
| `heightCm` | `number` | 是 | 身高（cm） |
| `weightKg` | `number` | 是 | 当前体重（kg） |
| `targetWeightKg` | `number` | 是 | 目标体重（kg） |
| `targetWeeks` | `number` | 是 | 目标期限（周），> 0 |
| `activityLevel` | `"sedentary" \| "light" \| "moderate" \| "high" \| "athlete"` | 是 | 对应系数 1.2 / 1.375 / 1.55 / 1.725 / 1.9 |
| `macroRatio?` | `{ protein: number; fat: number; carb: number }` | 否 | 百分比，默认 `{25,25,50}`，三者之和须 = 100 |
| `weeklyLossKg?` | `number` | 否 | 每周目标减重（kg）。未给则由 `weightKg/targetWeightKg/targetWeeks` 推导 |

### 5.2 计算规则

| 步骤 | 公式 |
| --- | --- |
| BMR（男） | `10 × weightKg + 6.25 × heightCm − 5 × age + 5` |
| BMR（女） | `10 × weightKg + 6.25 × heightCm − 5 × age − 161` |
| TDEE | `BMR × activityFactor` |
| 目标缺口 raw | `weeklyLossKg × 7700 ÷ 7` |
| 缺口上限 cap | `TDEE × 0.30` |
| 校验与告警分层 | **硬错误（阻断计算）**：`weeklyLossKg` 非有限值或 ≤ 0、枚举非法、数值越界、`macroRatio` 之和 ≠ 100；**非阻断告警（照常计算 + 温和提示）**：`weeklyLossKg > 体重 × 2%`（详细契约见 ARCHITECTURE §4.5） |
| 有效缺口 | `min(rawDeficit, cap)` |
| 建议摄入 raw | `TDEE − 有效缺口` |
| 安全下限 floor | `female → 1200`，`male → 1500` |
| 建议摄入 final | `max(rawIntake, floor)` |
| 宏量营养素 | 蛋白 = `final × protein% ÷ 4`g；脂肪 = `final × fat% ÷ 9`g；碳水 = `final × carb% ÷ 4`g |

### 5.3 输出 `CalorieResult`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `bmr` | `number` | 四舍五入到整数 kcal |
| `tdee` | `number` | 整数 kcal |
| `targetDeficitRaw` | `number` | 未截断的原始缺口 |
| `deficitCap` | `number` | TDEE × 30% |
| `effectiveDeficit` | `number` | 实际采用的缺口（可能被截断） |
| `isDeficitCapped` | `boolean` | 是否触发 30% 上限截断 |
| `intakeRecommended` | `number` | 最终建议摄入 |
| `floorApplied` | `boolean` | 是否触发安全下限 |
| `safetyFloor` | `number` | 1200 / 1500 |
| `safetyMessages` | `string[]` | 面向用户的安全提示文案（见 §8） |
| `macros` | `{ proteinG: number; fatG: number; carbG: number }` | 克数 |
| `weeklyLossEffectiveKg` | `number` | 按最终摄入反推的每周实际减重 |
| `etaWeeks` | `number \| null` | 按有效缺口预测达成目标所需周数 |

**边界与顺序约定（必须实现且必须测试）**：先算 `effectiveDeficit = min(raw, cap)`，再算 `intake = max(tdee − effectiveDeficit, floor)`；**下限的优先级高于缺口上限**。两个标志位可同时为 `true`。

### 9.2 导出 CSV

- 每个实体一个文件，统一使用 UTF-8 with BOM，首行为表头，日期为 `YYYY-MM-DD`。
- 文件清单：`weights.csv`、`meals.csv`、`exercises.csv`、`habits.csv`、`water.csv`、`wins.csv`（`wins.csv` 列：`date`、`text`，正文按 RFC 4180 转义逗号/引号/换行）。

### 9.3 CSV 导入模板（历史体重）

| 列名 | 必填 | 说明 |
| --- | --- | --- |
| `date` | 是 | `YYYY-MM-DD` |
| `weightKg` | 是 | 数字，0 < w < 500 |
| `note` | 否 | 文本，≤ 200 字 |
