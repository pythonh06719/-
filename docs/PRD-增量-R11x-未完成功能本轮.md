### 2.2 决策：「N9 身体围度记录」→ **本轮不做**

候选清单 §4.2 定下的规则是「四条规避条件**缺一则不做**」。逐条核实结果：

| # | 规避条件 | 技术上能否满足 | 结论 |
| --- | --- | --- | --- |
| ① | 不给任何参考区间 / 标准值 | ✅ 可满足（只画自身趋势、不写参考值） | 不构成阻塞 |
| ② | 不与体重合并成综合评分 | ✅ 可满足 | 不构成阻塞 |
| ③ | 可完全关闭 | ✅ 可满足（加设置开关 + 硬删除） | 不构成阻塞 |
| ④ | 不主动提醒测量 | ✅ 可满足 | 不构成阻塞 |

**四条全部可以满足，但结论仍然是不做。** 理由不在四条之内，而在四条之外：

1. **第①条守不住语义的扩散。** 产品可以不给参考值，但只要存在一条「腰围趋势线」，
   用户会自发去寻找外部参考值并自行评判 —— 产品无法控制**展示之外的语义**，而这恰恰是 §4.2 担心的焦虑来源。
   相比之下 R11.4（非体重胜利）把同一诉求「体重不动但身体在变」交给用户自己的语言来表达，
   「裤子松了一圈」在语义上**已经覆盖了围度改善**，但它是用户的叙述，不是被测量的数字。
2. **已经有更轻的替代路径，且本轮才刚落地。** §4.2 自己写的验证顺序是「先 N6 再 N9」——
   N6 本轮才上线，**尚无任何证据**表明用户真的需要非体重进步信号。在数据为零的情况下投入
   「新表 + 趋势图 + 设置项 + 导出/删除联动」的中成本功能，违反最小验证原则。
3. **它与本轮主题的优先级冲突。** 本轮是「把没做完的做完」，而 N9 是一个**全新的重功能**，
   不是未完成项。用它挤占 R3.8（P0 未完成）与 N5/N6 的工期不划算。

> **解锁条件（写死，供下一轮评估）**：R11.4 上线并稳定运行后，若用户在「体重之外的变化」中
> 累计记录 ≥ 20 条、且其中 ≥ 5 条涉及身体维度类叙述（裤子/腰/衣服松了），则 N9 升为下一轮第一候选立项；
> 否则继续保持 Out。此判据是对产品行为的观察，不需要问用户。

### 2.3 决策：「R1.2 微信扫码登录」→ **本轮不纳入，编号保留在原需求池**

1. **它的阻塞不是开发工作量，而是外部资质。** 微信扫码登录需要微信开放平台账号、AppID/AppSecret、
   已备案域名与合规主体资质。这是**资源与合规依赖**，本轮排期无法解决，排了也交付不了。
2. **与当前使用场景不匹配。** 主要使用者是用户本人单人长期记录，需求池已有 R1.1（邮箱 + 验证码）满足登录诉求；
   扫码登录的收益是「降低注册摩擦」，而单人自用场景下新用户注册几乎不发生。
3. **引入第三方身份提供方需要重算隐私口径。** 隐私承诺（NFR-6/R10.5）明确「不出售数据、无第三方行为分析」，
   接入微信身份需要额外对齐。收益小、成本高，且引入的是一个**外部依赖**。

> **处置**：R1.2 **保持原有编号与 P2/三期分期不动**，不重新编号、不进入本轮；若后续用户仍需，
> 单独立项评估主体资质。**本增量文档不修改 R1.2 的任何内容。**

## 4. 需求详述

### 4.1 R3.8 · 餐间拖拽排序（既有 P0，本轮补齐）

**需求说明**：`/diary` 的一餐条目支持拖拽**调整顺序**，并支持把一条记录**拖到另一餐**（跨餐移动）。
DB 侧 `meal_logs.sort_order` 列已存在，本轮补齐「缺的三样」：API 排序/移动接口、UI 拖拽交互、sortOrder 分配口径。

> **为什么它是本轮第一优先**：需求池中唯一一个 **P0 未实现**项，TC-27 已把「两餐热量预算同步更新」写进验收用例。
> 它的价值不是新功能，而是**把已经承诺过的东西兑现**。

#### 用户故事

- **US-3.8.1**：As a 记录型用户，I want 把一餐里的条目按我实际吃的顺序排好，so that 回头看的时候和我的记忆一致。
- **US-3.8.2**：As a 记错了餐次的用户，I want 直接把一条记录从「早餐」拖到「加餐」，so that 我不用删掉重记一遍。
- **US-3.8.3**：As a 使用屏幕阅读器 / 不方便长按的用户，I want 通过按钮完成同样的移动，so that 我能用得上这个功能。

#### 验收标准

| ID | 验收标准（可测） | 优先级 |
| --- | --- | --- |
| AC-3.8.1 | **拖拽范围**：支持 ① 同一 `loggedDate + mealType` 内的**顺序调整**；② 跨 `mealType` 的**移动**（拖到目标餐即变更 `mealType`）。两者都必须实现，只做其一视为不通过（TC-27 要求跨餐） | P0 |
| AC-3.8.2 | **跨餐语义**：跨餐移动后 `mealType` 变更为目标餐；该记录的 `kcal / proteinG / fatG / carbG` **一律不变、不重算**；源餐与目标餐的小计、餐次预算进度在同一帧内同步刷新，无需手动刷新页面 | P0 |
| AC-3.8.3 | **API 契约**：新增 `PATCH /api/meals/reorder`，body `{ loggedDate: 'YYYY-MM-DD', mealType: 'breakfast'\|'lunch'\|'dinner'\|'snack', orderedIds: number[] }`；服务端**原子地**把列出的记录置为目标 `mealType` 并按 `orderedIds` 顺序赋 `sortOrder = index`。幂等：重复提交同一 payload 结果一致。返回被更新记录的 `[{ id, mealType, sortOrder }]` | P0 |
| AC-3.8.4 | **鉴权与入参校验（NFR-2）**：`userId` 一律从 JWT 取，忽略请求体中的任何 userId；`orderedIds` 中含不属于当前用户的 id → **404**（不暴露他人资源）；含不存在的 id → 400 且**明确说明是哪一个**；重复 id 去重后处理（不报错）；空数组 → 200 no-op | P0 |
| AC-3.8.5 | **sortOrder 分配口径（必须修改现有行为）**：新增 meal 记录时，前端**不传** `sortOrder`（保留现有 `sortOrder: 0` 的 payload 无害），由服务端计算为「该用户·该日·该餐当前最大 `sortOrder` + 1」。列表读取一律按 `sortOrder ASC, id ASC` 排序。**不修这条会导致：拖过顺序之后新记的一条永远排在最前面** —— 这是本条最容易被漏掉的实现陷阱 | P0 |
| AC-3.8.6 | **移动端可用性（NFR-9）**：触屏必须可**长按**（≥ 300ms）触发拖拽，不得把 HTML5 `draggable` 作为唯一手段（移动端 WebKit / Android Chrome 支持不可靠）。拖拽期间提供明确的视觉反馈（抬起 + 描边），不改变任何热量数值 | P0 |
| AC-3.8.7 | **非拖拽降级路径（NFR-7，硬性）**：每个条目必须同时提供一组**可点击控件**完成等价操作 ——「上移 / 下移」+「移动到（早餐/午餐/晚餐/加餐）」。该组控件必须可被屏幕阅读器读作完整语句（如「把番茄炒蛋移动到午餐」）、满足 WCAG AA 对比度与 `qsh-touch-target` 触控尺寸。**没有降级路径即判定不通过** | P0 |
| AC-3.8.8 | **零新增运行时依赖**：本条默认手写 Pointer Events 实现（项目已有手写 SVG 图表先例）。若架构师评估确有必要引入库，须**书面说明理由**且新增 gzip ≤ 10KB，并在 ARCHITECTURE 中登记 | P1 |
| AC-3.8.9 | **乐观更新 + 失败回滚**：提交采用乐观更新；离线时沿用现有 `enqueueRequest` 离线队列；失败或离线排队时 UI 回滚到拖拽前顺序，并给出中性提示「这次没有移动成功，稍后再试试」（**不得**以「失败」作标题、不得用红色警示语义）。重新拉取后一律以服务端顺序为准 | P1 |
| AC-3.8.10 | **单测（`@qsh/core` 纯函数）**：新增 `applyReorder(items, targetMealType, orderedIds)` 纯函数输出新的 `mealType` / `sortOrder` 映射。必须覆盖：跨餐移动 / 目标餐为空 / 顺序完全反转 / 未知 id 被忽略 / 重复 id 去重 / 部分 id（其余保持原样） | P0 |

### 4.3 R11.4 · 体重之外的变化（非体重胜利）

**需求说明**：一个极轻量入口，随手记一条与数字无关的正向变化（「今天爬楼不喘了」「裤子松了一圈」）。
**需要新增数据表 `win_logs`**。

#### 为什么必须新表（而不是复用 `weight_logs.note`）

1. `note` 的语义是「**那一条体重记录的上下文**」，只有当日记了体重才存在；而 N6 要求「今天没称重也能记」。
2. 它需要**独立的时间线回看**（列出所有记录），这是备注字段做不到的。
3. 它需要独立参与导出 / 硬删除 / 隐私边界的处理（复用备注会让「彻底删除」的边界变模糊）。
→ **结论：新增 `win_logs` 表。**

#### 用户故事

- **US-11.4.1**：As a 处在平台期的用户，I want 记下体重之外的改善，so that 体重不动的时候我也能看到自己在往前走。
- **US-11.4.2**：As a 不想被游戏化绑架的用户，I want 它只是一个随手能写一句话的地方，so that 它不会变成另一份需要完成的作业。

#### 数据模型变更

```prisma
// win_logs —— 体重之外的变化（R11.4）
model WinLog {
  id         Int    @id @default(autoincrement())
  userId     Int    @map("user_id")
  loggedDate String @map("logged_date") // 'YYYY-MM-DD' 本地日粒度
  text       String                     // 正文，≤ 60 字（应用层校验，DB 不约束长度）
  createdAt  String @default(dbgenerated("(strftime('%Y-%m-%dT%H:%M:%fZ','now'))")) @map("created_at")
  updatedAt  String @default(dbgenerated("(strftime('%Y-%m-%dT%H:%M:%fZ','now'))")) @map("updated_at")

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId, loggedDate], map: "ix_win_user_date")
  @@map("win_logs")
}
```

> **刻意不加 `(userId, loggedDate)` 唯一约束**：同一天允许多条。这是「随手记」而不是「每日打卡」，
> 加唯一约束会把它变成一天只能完成一次的任务（直接违反约束 3）。

### 4.5 R11.6 · 备份缺口补齐

**需求说明**：N8 的基座已经在 C6 落地（见 §2.4）。本条**只做缺口**：≥30 天未备份的温和提示 + 记录概览（数据健康自检的最小版本）。
同时把已实现部分写成**回归保护**，防止后续重构把它改没。

#### 明确定为 Out 的三件事（含理由）

| 子项 | 结论 | 理由 |
| --- | --- | --- |
| **静默自动定期下载** | **Out** | 浏览器通常会拦截非用户手势触发的下载，做成就是不可靠；更重要的是，在用户没做任何操作时**替他生成一个文件**违背 NFR-10「不主动」的精神。可行性缺点是次要的，产品伦理才是主要理由。保留「进入数据管理页时看到一行提示 + 一键备份」这条路径 |
| **任何云端上传 / 同步 / 对象存储** | **Out（硬性）** | 引入云端会破坏隐私承诺（不出售数据、无第三方）并带来成本与合规负担。见 AC-11.6.9 的可校验约束 |
| **离群值 / 异常值检测** | **Out（本轮）** | 「异常」这个词本身就是一种评判 —— 它暗示用户的记录**错了**。而定义「离群」需要阈值，任何阈值都会变成用户看不见的隐性标准，这与「每个数字可解释」（NFR-11）相冲突：既要解释，就必须解释得比它带来的价值更值。本轮改为做**中性的记录概览**（只陈述事实：有几条、跨度多久），把「我的数据都在吗」这个真实问题回答掉，而不去评判任何一条记录有问题 |

#### 用户故事

- **US-11.6.1**：As a 一个人用的用户，I want 在数据管理页看到「多久没备份了」并被温和地想起这件事，so that 我不会被一个弹窗吓到，但也不至于忘干净。
- **US-11.6.2**：As a 关心数据安全的用户，I want 看到我到底存了哪些、存了多久，so that 我知道我的记录都在。

## 8. 依赖顺序与建议实施批次

### 8.1 依赖关系

```
① packages/core 纯函数层（零 IO，先于一切，可并行写单测）
     distinctFoodKeys ──→ R11.7 多样性 ──┐
     distinctFoodKeys ──→ R11.3 回顾（口径必须同源）
     rankFrequentFoods ─→ R11.5 常吃榜（依赖上面的 identity 口径）
     summarizePeriod ───→ R11.3 阶段回顾
     applyReorder ──────→ R3.8 拖拽
     normalizeWinText ──→ R11.4 非体重胜利
     backupHintCopy ────→ R11.6 备份提示（位于 apps/web/src/lib/copy.ts）
                  ↓
② 数据层：win_logs 迁移 + export schemaVersion 2   [仅 R11.4 需要]
                  ↓
③ API 层：§6.3 的六个新增 / 扩展接口
                  ↓
④ UI 层：MealComposer(R11.5) / Diary(R3.8) / Report(R11.3,R11.5,R11.7)
         / Weight(R11.4) / SettingsData(R11.6)
                  ↓
⑤ /why-numbers 条目（随各条同步交付，不得最后补）
```

**关键依赖**：
- `distinctFoodKeys` 是 **R11.7 → R11.3** 的硬前置：两者口径必须一致，先做 R11.7 更划算（成本低、门禁清晰）。
- `rankFrequentFoods` 依赖同一套 identity 口径，因此 **R11.5 必须排在 R11.7 之后**。
- **R11.4 是全表唯一的 DB 迁移**，迁移完成后才谈得上 export v2 与 `/data/overview`。
- **R3.8 与其余 5 条互相独立**，但它有隐藏依赖：`sortOrder` 分配规则的修改（AC-3.8.5）会触及新增 meal 的服务端路径，
  建议**不要在 R11.x 的 /diary 改动同时进行**，避免同一处代码的两批改动互相打架。

### 8.2 建议批次

| 批次 | 内容 | 理由 |
| --- | --- | --- |
| **批次 1（先做，P0/P1 地基）** | `distinctFoodKeys` + **R11.7 多样性** + **R3.8 拖拽补齐** | R3.8 是全需求池唯一 P0 未完成项，风险最高、最该先啃；R11.7 成本最小且产出共用口径 |
| **批次 2** | **R11.3 阶段回顾** + **R11.5 常吃榜** | 共用 identity 与 /report 页面结构；一次性把 `/report` 的标签页框架做完，避免二次改版 |
| **批次 3** | **R11.4 非体重胜利**（含迁移与 export v2） + **R11.6 备份补齐** | R11.4 是唯一需要迁移的项，放前面给 QA 留足时间；R11.6 几乎只在渲染层，随时可插队 |

> **`/why-numbers` 条目必须与所在批次同步交付**，不允许「功能先上、解释后补」——这是 NFR-11，也是本产品最重要的差异化。
