## 1. 审计方法

### 1.1 覆盖范围

| 层面 | 检查对象 |
| --- | --- |
| 前端路由 | `apps/web/src/router/routes.tsx`（14 条实路由 + 1 条兜底），逐条确认页面职责与真实实现度 |
| 前端页面 | `apps/web/src/pages/**`（14 个页面目录，共约 9,340 行 tsx） |
| 后端路由 | 16 个 `*.controller.ts`，提取全部 `@Get/@Post/@Patch/@Delete` 路由（约 80 条） |
| 前后端对照 | 全仓 grep 所有 `api.get/post/patch/delete` 与 `postStream` 调用，与后端路由**逐条求差集** |
| PWA / 离线 | `vite.config.ts` 的 `VitePWA` 配置、`src/pwa/service-worker.ts`、`public/manifest.webmanifest`、`offline-queue.ts` |
| 承诺对照 | `apps/web/src/lib/copy.ts` 中「自动 / 随时 / 支持 / 可完整 / 同步」类措辞，与 `docs/PRD.md` 需求池逐条核对 |

### 1.2 判定口径

- **断链**：后端有接口、前端零调用；或前端有 UI、后端无接口；或数据存了但从不展示。
- **半成品**：功能做了但差一口气（缺创建入口 / 缺删除入口 / 缺空态 / 只有一条路径能到）。
- **承诺未兑现**：PRD 或 UI 文案承诺了某事，代码里没有。
- **该有而无**：自用场景真实需要、但产品里完全没有入口。

### 1.3 关键对照方法（可复现）

```
# 后端全部路由
grep -rnE "@(Get|Post|Patch|Put|Delete)\(" apps/api/src --include="*.controller.ts"

# 前端全部 API 调用路径
grep -rnoE "(api\.(get|post|patch|delete)|postStream)(<[^>]*>)?\('[^']*'" apps/web/src
# → 对两条结果求差集，即得「后端有、前端无」的候选断链
```

## 4. 最推荐的 2~3 个

### 🥇 GAP-1 收藏只读不写 + 🥈 GAP-2 套餐只能看不能建（建议合并为一个「P0 需求补完」批次）

**理由**：这两条是同一类问题、同一处代码（`MealComposer.tsx`）、同一优先级（都是 **P0**），且都是「后端齐全、只差前端接线」——**修复成本最小、收益最直接**。

- PRD 明确把「收藏」（`R3.4`）与「套餐模板（常吃一餐存为组合）」（`R3.9`）列为 **P0**，但两条都**只交付了一半**；
- 用户能看到「收藏」「套餐」两个 Tab，却永远填不满它们 —— 这是**看得见的残缺**，比「没有这个功能」更伤信任；
- 修复无需任何后端改动，前端各加一个入口即可。

### 🥉 GAP-4 设置（单位/深色）不落库 + 导出「可完整恢复」名不副实

**理由**：它是**唯一一条「文案已承诺、行为却相反」**的缺口，牵涉产品最核心的「数据主权 / 可解释 / 可恢复」三处承诺。

- 导出页白纸黑字写「**JSON 可完整恢复**」，但用户的单位与深色模式**根本不在导出里**（前端写死默认值 `csv.ts:141`）；
- 后端 `/users/settings` 早已具备读写能力，只差前端接线 —— 属「该建未建」的桥；
- 补上它，导出/恢复才真正闭环，也顺带为「换设备延续偏好」铺路。

> 若只能做一件：**先做 GAP-1**（成本最小、P0 需求缺口、用户可见）。若做一批：**GAP-1 + GAP-2 + GAP-4**（三条都是「后端已好、前端差一口气」的接线活，可一次交付）。
