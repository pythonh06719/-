## 2. 候选详述

### C-1 · 记录足迹日历（全局月历）

| 字段 | 内容 |
| --- | --- |
| **一句话** | 一张**月历**：有记录的日期点亮，点任意格子直接跳到那一天的档案；一眼看见「这个月我记了 22 天」。 |
| **解决的真实痛点** | **场景**：单人长期记录，没有他人监督，最大的流失信号不是「记错了」而是「**忘了自己在坚持**」。月底想回顾时，用户找不到一个「我这些天到底记了没有」的整体视图 —— 只能一天一天点进去（`/diary` 的 `‹ 今天 ›`、`/weight` 的记录列表、`/habits` 的单习惯格）。**现有日历全是单维度的**：`HabitCalendar` 只看某一个习惯；`/report` 只有周/30 天/365 天的聚合数字，没有「哪几天」的落点。结果是「付出感」被摊薄成了一堆孤立数字。 |
| **产品形态建议** | 新增 `/calendar`（或在 `/report` 加第三个 tab「足迹」）。**网格 = 当月日期**，每格用**深浅**表示当天记录充实度（如：只记了体重 = 浅，记了饮食 + 体重 = 深）。**只表示「有没有记 / 记了多少类」，不表示好坏、不表示热量高低**。点格 → 复用 N2 的一日档案（`/day` 或现有按日回看）展示当天全部内容。**不显示**「连续多少天」「断了几次」「完成率」。 |
| **与调性的契合度** | ★★★。**正确做法**：把它做成一本**打卡集邮册**——只呈现「记录本身」的存在感，颜色深浅表达的是「丰富度」不是「分数」；缺记录的日子**留白**（不填灰、不画叉、不显示「未完成」）。<br>⛔ **明确反对的做法**：① 做成 GitHub 那种带「连续 streak」的热力图（会立刻把留白变成压力，PRD §7 已把「不能断」列为反例）；② 用红色/警示色标记无记录日；③ 显示「本月完成率 71%」这类百分比评分 —— 一旦有分母就是评判。 |
| **风险与规避** | **中**。风险全在「呈现方式」上，不在数据上。规避四条：① 无分值 / 无百分比 / 无连续计数（硬性）；② 无记录日留白，不用任何负向视觉；③ 颜色映射口径必须写进 `/why-numbers`（NFR-11 硬约束）；④ 只在用户**主动进入**时展示，绝不主动弹窗（NFR-10）。 |
| **优先级建议** | **P1**。它是「自用场景深层诉求」里**最直接的一刀**：单人没有观众，唯一的反馈就是自己能不能看见自己的积累。成本不高，收益是每次月度回顾都发生的。 |
| **大致成本** | **小→中**。api：一个按日 + 按模块聚合的「哪些天有记录」只读查询（复用 meals/weights/water/habits 的按日聚合，N2 已有类似能力）；web：月历网格 + 深浅映射 + 点击跳转。**无需新表。** |
| **是否与现有功能重复** | **不重复。** `HabitCalendar` 是**单个习惯**的 7×5 网格，属 habits 页局部；本项是**跨全部记录模块**的**整月**视图，回答的是「我整体记不记得住」这一层问题。`/report` 的 30/365 是**聚合数字**，不提供逐日落点。三者维度不同，互为补充而非替代。 |

### C-2 · PWA 应用快捷方式（长按图标直达）

| 字段 | 内容 |
| --- | --- |
| **一句话** | 在手机/桌面上长按「轻生活」图标，弹出「记一餐 / 称体重 / 喝一杯水」三个直达入口，点一下跳过首页。 |
| **解决的真实痛点** | **场景**：晚上站在体重秤旁想记体重，打开 App → 等首屏 → 点「变化」→ 才到记录框 —— 中间三步都是**为了记录而做的时间税**。G1 的目标是「≤3 次点击记一餐」，但那 3 次是**页面内**的点击；**到达那个页面本身**的成本没被算进去。单人自用时，记录的**启动摩擦**往往比页面内那几步更能决定「今天到底记不记」。 |
| **产品形态建议** | 纯 **manifest 能力**：在 `public/manifest.webmanifest` 增加 `shortcuts`（三个：`/diary?focus=record`、`/weight?focus=record`、`/dashboard?water=1`），配合现有的路由接收一个「聚焦参数」自动把记录面板打开 / 触发一次快捷动作。**不改任何业务逻辑**，只在页面挂载时按参数聚焦。 |
| **与调性的契合度** | ★★★。**正确做法**：快捷方式只是**缩短到达路径**，不产生任何新数字、新评价、新提醒；它是「让记录这件事更便宜」的中性加速。<br>⛔ **明确反对的做法**：① 把快捷方式做成「催促」（例如叫「快补上今天的记录」）—— 那是催办，踩 NFR-10；② 通过快捷方式在后台偷偷生成记录 / 弹通知。 |
| **风险与规避** | **低**。要点：① **不得**借快捷方式引入任何主动通知（NFR-10）；② 桌面端（Windows）浏览器对 PWA shortcuts 的支持不一，需**优雅降级**——不支持时应用一切照旧，不做提示、不报错；③ 聚焦参数要幂等（刷新不重复触发动作）。 |
| **优先级建议** | **P1**。成本极小、直接命中 G1，且是唯一一个**同时服务手机与 Windows 桌面**的入口优化。 |
| **大致成本** | **小**。`manifest.webmanifest` 加 `shortcuts` 字段 + 相关页面读取一个 query 参数做聚焦。**无后端改动。** |
| **是否与现有功能重复** | **不重复。** 现有 `BottomNav` 四入口是**应用内**导航；本项是**应用外**（系统级图标菜单）的到达路径，两者叠加而非替代。 |

### C-3 · 一餐多品项批量记录（一次勾选多样）

| 字段 | 内容 |
| --- | --- |
| **一句话** | 记麻辣烫/火锅/自助时，在一个列表里**一次勾选十几样**，统一确认后一起入账，而不是一样一样地搜。 |
| **解决的真实痛点** | **场景**：S1「午餐点麻辣烫，边吃边记」。麻辣烫一餐可能就是十几样：宽粉、豆腐皮、青菜、鱼豆腐、鹌鹑蛋……现有链路（R3.4）是**一样一样搜、一样一样选份量、一样一样确认**，十几样就是几十次操作。用户的实际反应不是「慢慢记」，而是**「算了，记两样代表一下」甚至干脆不记** —— 这直接击穿 G1，也污染了 R11.5 常吃榜与 R11.7 多样性计数的数据质量。 |
| **产品形态建议** | 在 `/diary` 的记录面板加一个「**多选模式**」开关：打开后，搜索结果**点击即加入待记清单**（不立即入库），清单里可逐项调份量，最后**一次确认**全部写入该餐次。清单可**临时保存为套餐**（与 R3.9 衔接，但**不强制**）。 |

| **优先级建议** | **P1**。它直接决定「一餐多样」这类**中式主食场景**（麻辣烫/火锅/自助/食堂打菜）到底记不记得下去，是 G1 在真实生活里最能翻车的一处。 |

| **是否与现有功能重复** | **不重复，三者本质不同**：① **套餐模板（R3.9）** 是**预先保存的固定组合**，可跨天复用，但要求用户**提前存**；② **聚餐模式（R5.3）** 是**估算器**（给区间 + 建议），**不写真实记录**；③ 本项是**临时的、一次性的多品项真实记账**，零预维护 —— 覆盖前两者都覆盖不到的「今天这顿十几样、下次未必重复」的场景。 |

## 4. 最推荐的 2~3 个

### 🥇 第一推荐：**C-1 记录足迹日历（全局月历）**

**理由**：它正面回答了这个探索任务的核心问题 —— **「单人没有观众，付出感如何被看见？」**
现有的时间维度全是「数字」或「单维度格子」：`/report` 给你「记了 22 天」，`HabitCalendar` 只给你某一个习惯的格子。**没有任何一个视图能让用户一眼看到「我这些日子是怎么走过的」。** 而单人长期记录最真实、最沉默的流失点，恰恰是**「我好像一直在记，但又好像什么都没留下」**。
C-1 把散落的记录拼成一张**可见的足迹**，成本不高（复用 N2 的按日聚合，无新表），却是「付出感」从抽象变具体的一次性工程。

### 🥈 第二推荐：**C-3 一餐多品项批量记录（一次勾选多样）**

**理由**：它是 G1「记一餐足够便宜」在**中式真实生活**里最容易翻车的一处，且现在**确实没有**覆盖。
麻辣烫 / 火锅 / 自助 / 食堂打菜 —— 这些一餐十几样、样样都要搜的场景，是目前产品里**唯一会让用户「因为太麻烦而放弃记录」的地方**（套餐模板要提前存、聚餐模式只估算不记账，都救不了它）。
更关键的是：**它同时提升了下游数据的质量** —— 用户肯老老实实记全，R11.5 常吃榜和 R11.7 多样性计数才不是「记了两样代表一下」的失真结果。

### 🥉 第三推荐：**C-2 PWA 应用快捷方式**

**理由**：**投入产出比最高的一条，且是唯一同时服务手机与 Windows 桌面两条线的。**
成本极小（一个 manifest 字段 + 页面读一个参数），却把「记体重 / 记一餐 / 喝一杯水」的**到达成本**砍掉一整屏。G1 承诺的是「3 次点击记一餐」，但用户真正在意的是**「我今天要不要记」的那一念之间**——让这一念到落账的距离越短，记录才越可能发生。
它和 C-1 是一对：**C-2 降低「记」的门槛，C-1 放大「记」的回报** —— 一个管入口，一个管回头。

> 建议评估顺序：**C-1 / C-3（价值密度最高）→ C-2（最便宜的收益）→ C-4 / C-5 / C-6（按意愿与工期弹性取舍）**。
